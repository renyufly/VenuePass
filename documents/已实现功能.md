# VenuePass 当前已实现功能

按当前仓库中的代码、数据库迁移脚本和部署配置整理。接口的请求参数与响应示例见 [API.md](API.md)。“已实现”指代码中存在对应逻辑。

## 1. 身份与访问控制

- 普通用户可通过用户名、密码注册；用户名限 3–40 位英文字母、数字或下划线，密码至少 8 位，密码以 BCrypt 哈希保存，用户名在数据库中唯一。
- 使用 HTTP Basic 登录。普通用户账号从数据库读取；运营人员 `operator` 和核销人员 `checker` 由环境变量密码提供。
- 接口按角色限制访问：运营人员负责资源与支付管理，核销人员负责入场核销，普通用户负责自己的预约。普通用户只能查看或取消自己的预约。
- 未登录和无权限请求由 Spring Security 拦截；健康检查和注册接口可匿名访问。

## 2. 场馆、活动和场次

- 运营人员创建场馆，填写名称、地址和容量；已登录用户可查看场馆列表。
- 运营人员在已有场馆下创建活动，填写标题与可选描述；已登录用户可查看启用的活动。
- 运营人员为活动创建场次，配置开始/结束时间、价格、容量及是否为热门场次；已登录用户可按活动查看场次。
- 创建时校验场次开始时间晚于当前时间、结束时间晚于开始时间、价格非负、容量不超过场馆容量。
- 场次保存总库存、可用库存和锁定库存；新场次初始状态为 `OPEN`，可用库存等于总库存。
- 运营人员可以取消开放中的场次，并批量处理其中待支付和已支付的预约。已核销预约不在此批量处理范围内。

## 3. 普通场次预约

- 普通用户提交参与人姓名和场次 ID 后，同步生成预约，记录用户、价格快照、唯一核销码、创建时间及支付截止时间。
- 创建时要求场次存在、开放且尚未开始。数据库通过带 `available > 0` 条件的库存更新扣减名额、增加锁定库存，避免并发超卖。
- 数据库唯一约束保证同一用户同一场次只保留一条预约记录；取消后也不能再次预约该场次。
- 普通用户可按时间倒序查看自己的预约列表及单条预约详情。
- 预约创建和后续状态变更写入 `reservation_event` 审计表，记录原状态、新状态、操作者和时间。

## 4. 热门场次预约

- 运营人员可在开放热门场次前，显式将数据库可用库存预热到 Redis；同一场次不能重复预热。未预热的热门场次拒绝提交。
- Redis Lua 脚本在一次原子操作中检查剩余名额和用户占位，并预扣 1 个名额；重复排队与售罄请求会被拒绝。
- 预扣成功后向 Kafka 发送预约请求，接口返回 `QUEUED`。普通用户可查询自己的排队结果：排队中、确认并返回预约 ID、或失败及原因。
- Kafka 消费者使用与普通场次相同的数据库条件库存更新和预约唯一约束创建订单；重复消息发现已有有效预约时复用该结果。
- Kafka 业务处理失败时释放 Redis 占位；发送结果不确定时保留占位，避免消息已入队却提前返还库存。
- 热门预约取消后的 Redis 释放有数据库重试记录，定时任务会在 Redis 暂时不可用后继续尝试。

## 5. 支付、超时、取消与退款状态

- 新预约进入 `PENDING_PAYMENT`，默认有 15 分钟支付期限，可通过 `PAYMENT_MINUTES` 配置。
- 运营人员可登记**外部已经确认**的支付及唯一交易编号；只接受未过期的待支付预约，成功后进入 `PAID`。
- 定时任务约每 60 秒扫描超时待支付预约，将其改为 `CANCELLED` 并释放库存；并发状态变更使用行锁和原状态条件更新。
- 用户可取消自己的待支付预约，状态变为 `CANCELLED` 并释放库存。
- 用户取消已支付预约或运营人员取消整个场次时，相关已支付预约进入 `REFUND_PENDING`，释放库存并标记需要退款。
- 外部退款完成后，运营人员可登记唯一退款编号，将 `REFUND_PENDING` 改为 `REFUNDED`。
- 状态变化与库存变化在数据库事务中执行；热门场次的 Redis 占位在事务提交后释放，并由数据库记录支持重试。

## 6. 入场核销

- 运营人员或核销人员可提交预约核销码和设备标识进行入场核销。
- 只有 `PAID` 预约、`OPEN` 场次，且当前服务端时间处于该场次开始与结束时间之间时才能核销。
- 核销成功后预约进入 `CHECKED_IN`，记录核销人员、设备和时间，并减少锁定库存。
- 预约状态校验和 `verification.reservation_id` 唯一约束共同阻止同一码重复核销。

## 7. 运营报表与运维接口

- 运营人员可按场次查询累计预约记录数、当前已支付或已核销数、已核销数，以及当前已支付或已核销预约的金额合计。
- 报表中的预约总数包含已取消和退款记录；金额不是历史总成交额。没有预约记录时返回 `null`。
- 提供 Spring Boot Actuator 健康检查、信息与 Prometheus 指标端点；指标端点仅运营人员可访问。
- 使用统一的业务结果对象返回 `code`、`msg`、`data`。业务异常与唯一键冲突转为业务错误响应。

## 8. 数据、构建与部署

- `frontend/` 提供 Next.js 单页演示界面：普通用户可注册、浏览活动、预约、查询热门排队结果及查看/取消自己的预约；运营人员可创建场馆、活动和场次、预热热门库存、登记支付/退款、取消场次及查看报表；核销人员可提交核销码与设备标识。
- 前端通过 Next.js 同源路由将请求转发给后端，浏览器无需单独配置后端 CORS。登录凭据只保存在当前页面内存，刷新页面即退出。
- 使用 MyBatis 访问 MySQL，Flyway 在首次启动时创建场馆、账号、活动、场次、预约、支付、状态审计、核销和库存释放记录表，以及相关外键和唯一约束。
- 保留三模块 Spring Boot 项目结构：`venuepass-common`、`venuepass-pojo`、`venuepass-server`。
- 提供多阶段 Dockerfile 和 Docker Compose，可一同启动演示前端、后端应用、MySQL、Redis 和 Kafka；配置可通过环境变量覆盖。
- 已有 6 个服务层单元测试，覆盖售罄拒绝、价格与到期时间快照、超时库存释放、核销码一次使用、已支付取消和 Redis 释放重试。Java 25 / Maven 3.10.0 的 `package` 构建及这些测试已通过。

## 9. 当前能力边界

- 支付和退款接口只**登记外部已完成的交易**；项目没有支付渠道接入，也不会直接扣款或发起退款。
- 当前没有活动或场次编辑/删除、通知发送、实名资格限制、会员等级/年龄/地域规则、预约明细商品、报表导出或管理后台页面。
- Compose 提供本地容器部署；当前仓库没有 Kubernetes 清单，也没有 Prometheus/Grafana 服务部署。
- 已通过构建与单元测试；本机 Docker 守护进程未运行，尚未完成 MySQL、Redis、Kafka 的真实联调。因此 Redis/Kafka 并发及故障恢复效果不能视为已通过集成验证。
